# Development phases

The project was built in fourteen phases, each of which is independently
runnable and testable rather than a slice of a monolith that only works at the
end. The git history follows them.

Every phase from 1 onwards produces something you can run on a phone and
watch. No phase is a mock: the stack has always processed real camera frames
and real sensor data, with capabilities absent rather than faked.

| Phase | What it added | Runnable result |
|---|---|---|
| 1 | Core primitives, camera capture, calibration, IMU/GPS fusion | Camera preview with live fused speed, heading and yaw rate. |
| 2 | Model abstraction, registry, detection, NMS, YOLO decoding | Bounding boxes, or an explicit "no detector installed" state. |
| 3 | Multi-object tracking with ego compensation | Stable identities, distance, relative velocity. |
| 4 | Bird's-eye transform, lane detectors, segmenters, road edges, NO_LANE_MODE | Lane overlay, drivable-area overlay, corridor when markings are absent. |
| 5 | Depth map, neural estimator, five-cue fusion | Distances with meaningful confidence, with or without a depth model. |
| 6 | Traffic signs, speed-limit reading, traffic lights, regulatory context | Signs and lights on the HUD; a speed limit that persists after the sign leaves frame. |
| 7 | World model, hazards, autonomy confidence | A single consistent scene model and the AUTONOMY CONFIDENCE LOW banner. |
| 8 | Route model, providers, matcher, navigation service | Turn-by-turn intent, working offline with a clearly-labelled direct line. |
| 9 | Sampling-lattice planner, collision prediction | Planned path drawn as a corridor; TTC and risk per object. |
| 10 | Rule-based decision engine | The decision, its reason and its confidence on screen. |
| 11 | Bicycle model, pure pursuit, PI longitudinal control | Steering, throttle and brake; the wheel turns. |
| 12 | Full HUD and ten screens; Android native TFLite layer | The complete application. |
| 13 | Recording and replay | Record a drive; replay it, or re-run the AI over it and diff. |
| 14 | Performance instrumentation | Per-stage budget, thermal and battery monitoring, tuning controls. |

## Running an earlier phase

Each phase is a commit. `git checkout` any of them and
`flutter run --release` — the app builds and runs at every point in the
history, and `flutter test` passes at every point.

```bash
git log --oneline          # phases are the commit subjects
git checkout <commit>
flutter test && flutter run --release
```

## What "runnable" meant at each step

The temptation in a project this size is to build the whole pipeline against
fabricated inputs and only connect the camera at the end. That was avoided
deliberately, because the bugs that matter here live precisely in the
connections — frames of reference, timestamp alignment, what a stage does when
its input is missing.

Concretely:

- Phase 1 ran on a real phone with a real camera before any perception
  existed, so the camera timestamp/orientation/frame-dropping questions were
  settled before anything depended on them.
- Phase 3's tracker was tested against synthetic detections generated by
  projecting metric positions *through the same camera model the tracker
  inverts*, which is what caught the ego-motion frame error.
- Phase 4's lane detector was tested against rendered road scenes with known
  lane positions, curvature and dash patterns — which is why it can be said
  to recover −1.75 m rather than merely "find something".
- Phases 9–11 were tested end to end over hand-built world states, which is
  how the swept-footprint, uncertainty-asymmetry and lead-vehicle-blocking
  bugs were found before they ever reached a road.

## Test coverage by area

```
core/geometry, calibration     projection round-trips, horizon refusal,
                               confidence falloff, rescaling
tracking                       Hungarian vs brute force, identity through
                               occlusion, adjacent vehicles, ego compensation,
                               implausible-velocity rejection, refinement
road/lanes                     ground-truth lane recovery, curvature, dashed
                               classification, noise, adjacent lanes,
                               refusal on blank asphalt, geometry rejection
depth                          scale recovery from a synthetic MiDaS map,
                               outlier resistance, parallax validity gating,
                               vulnerable-road-user bias
planning                       centreline following, obstacle offsetting,
                               blocked detection, NO_LANE_MODE, path holding,
                               lateral rate limiting
collision                      risk levels, oncoming and adjacent traffic,
                               headway, crossing pedestrians and motorcycles,
                               uncertainty monotonicity
decision                       every state, hysteresis both directions,
                               degraded-subsystem reporting, JSON round-trip
simulation                     safety invariants, power-limited acceleration,
                               turn radius, steering rate limiting, control
                               convergence without overshoot
perception/signs               digit reading across scale and stroke weight,
                               rejection of noise and implausible values
recording/replay               schema round-trip, interrupted-session
                               recovery, pruning, world and path restoration,
                               truncated final line
```
